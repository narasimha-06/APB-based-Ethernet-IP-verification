## Ethernet IP Core Verification Plan :

The project focuses on the **functional verification of an Ethernet IP Core with an APB host interface**. The Ethernet IP supports **10 Mbps and 100 Mbps communication**, separate transmit and receive paths, DMA-based data transfer, buffer descriptors, interrupt generation, CRC-based error detection, and MAC-layer frame processing. The main objective of the verification plan is to ensure that the Ethernet IP operates correctly according to its specification under normal, boundary, and error conditions. The verification is primarily focused on the **Receiver (RX) path**, while also checking the interaction between the APB host interface, memory interface, buffer descriptors, and Ethernet MAC interface. The verification plan defines the verification environment, test scenarios, assertions, functional coverage, scoreboard checking, and regression strategy. 

The Ethernet IP is configured through the **APB interface**. Important registers include MODER, INT_SOURCE, INT_MASK, TX_BD_NUM, MIIADDRESS, MAC_ADDR0, and MAC_ADDR1. The verification plan checks correct reset values, register read/write operations, field-level behavior, and valid configuration sequences. The MODER register is particularly important because it controls features such as **RX enable, TX enable, promiscuous mode, broadcast filtering, and preamble configuration**. The MAC address registers are also verified because they together form the complete 48-bit individual MAC address used for destination-address filtering during frame reception.  

A major part of the verification is the **Buffer Descriptor (BD) mechanism**. The Ethernet IP uses 64-bit descriptors to control data movement between the Ethernet core and memory. The descriptors contain status/control information and a pointer to the memory location containing the frame data. The internal descriptor memory supports up to 128 descriptors, with the Tx and Rx descriptor regions determined using the TX_BD_NUM register. The verification environment therefore checks descriptor configuration, address calculation, ready/status behavior, frame length, and correct updating of descriptor information after packet reception. 

The verification environment is implemented using **SystemVerilog and UVM**. It follows a layered architecture that separates stimulus generation, protocol driving, monitoring, checking, and coverage collection. At the top level, the physical interfaces connect the DUT to the verification components. Virtual interfaces are used to provide UVM components with access to DUT signals. The top environment contains a **Host Environment, MAC Environment, scoreboard, and coverage components**. The Host Environment handles APB and memory-side activity, while the MAC Environment generates Ethernet receive traffic. 

The **Host Active Agent** consists of a sequencer, driver, and monitor. The host sequence performs register configuration through individual tasks. It generates APB transactions using `start_item()` and `finish_item()`. The Host Driver converts these transactions into APB signal activity and waits for the DUT's `PREADY` response before completing a transaction. This allows the verification environment to check both read and write operations and APB protocol behavior. 

The environment also contains a **Memory Active Agent and Memory Passive Agent**. The Memory Active Agent generates memory-side transactions, while the passive agent only observes memory activity without driving signals. The memory monitor reconstructs memory transactions from the interface and forwards them through an analysis port. This is useful for checking whether the Ethernet core correctly accesses memory during packet reception. 

The **MAC Active Agent** is responsible for generating Ethernet frames and driving them into the DUT. It contains a MAC sequencer, MAC driver, and MAC monitor. The MAC sequence constructs an Ethernet frame field by field, including the **preamble, SFD, destination address, source address, length/type field, payload, optional padding, CRC, and inter-frame gap**. The generated frame is stored in a nibble-based queue so that it can be driven according to the MII interface timing. The MAC driver then drives the frame nibble-by-nibble onto signals such as MRxD, with MRxDV indicating valid receive data.  

The **MAC monitor** is a passive component that continuously observes the Ethernet receive interface. It samples signals such as MRxD, MRxDV, MRxErr, and the receive clock. It reconstructs the received Ethernet frame and performs protocol-level processing. The monitor checks different stages of the frame, including preamble, SFD, destination address, source address, length, payload, CRC, frame status, and interrupt status. It also tracks error conditions such as preamble errors, SFD errors, destination-address errors, length errors, and frame-drop conditions. The reconstructed transaction is sent to the scoreboard and coverage collector through an analysis port. 

The **scoreboard is the main functional checking component** of the verification environment. It receives transactions from the monitors and compares expected information with the actual data observed from the DUT. For a valid frame, the scoreboard verifies that the received data matches the expected destination address, source address, length, payload, and other relevant fields. It also checks that frames are not unexpectedly lost or corrupted. This provides end-to-end data-integrity checking rather than depending only on individual signal-level checks. 

CRC/FCS verification is another important part of the plan. According to the Ethernet specification, the CRC is calculated over the destination address, source address, length/type, payload, and padding, excluding the FCS itself. During RX operation, the calculated CRC is checked against the expected result. The project specification also states that the final CRC comparison uses the reference value **32'hC704DD7B**; a matching result indicates a valid frame, while a mismatch causes the frame to be rejected. Therefore, the verification plan includes both valid-CRC and invalid-CRC scenarios. 

The verification plan includes a **good-frame test case** as the basic sanity test. In this test, the DUT is reset and configured through APB register writes. The RX function is enabled by programming the MODER register and configuring the receive buffer descriptor. A valid Ethernet frame containing the correct preamble, SFD, addresses, payload, and CRC is then driven through the MAC interface. MRxDV, MRxD, MCrS, and MRxErr are monitored to ensure that the frame is received without errors. The scoreboard checks data integrity, assertions check protocol behavior, and functional coverage confirms that the required scenarios have been exercised. 

Additional verification scenarios cover **register configuration, boundary conditions, protocol validation, and error handling**. Boundary testing is important for checking minimum and maximum frame lengths, payload sizes, buffer descriptor boundaries, address values, and control-field limits. Error scenarios include invalid CRC, incorrect preamble or SFD, invalid destination address, receive errors, and invalid frame-length conditions. The environment also verifies configurations such as promiscuous mode, broadcast filtering, RX enable/disable behavior, and different Ethernet operating conditions. The Ethernet specification requires the minimum inter-frame gap to be maintained, with different timing requirements for 10 Mbps and 100 Mbps operation. 

**SystemVerilog Assertions (SVA)** are used for protocol and signal-level checking. The assertion plan covers clock behavior, X/Z checks, APB protocol, memory-side APB protocol, register reset values, and register configuration restrictions. APB assertions verify correct setup and access phases, including PSEL, PENABLE, PREADY, address, and data stability. Clock assertions verify the expected timing of `pclk_i` and `MRxClk`, while unknown-state checks ensure that important signals do not become X or Z after reset. 

Finally, **functional coverage and regression** are used to measure verification completeness. Coverage is collected for APB control signals, register addresses, data patterns, MAC interface signals, individual register bits, cross combinations, and signal transitions. Data coverage includes patterns such as all zeros, all ones, `0x55555555`, and `0xAAAAAAAA`. Cross coverage checks interactions such as address versus read/write operation and PSEL versus PENABLE. Transition coverage verifies sequences such as reset transitions, enable/disable operations, wait-state behavior, and error-signal transitions. 

The final stage is **regression testing**, where all directed and constrained-random test cases are executed together. The regression includes valid-frame, register-configuration, boundary-condition, and protocol-validation tests. The final verification status is evaluated using **test results, scoreboard comparisons, assertion results, and functional coverage**. A successful regression requires all planned tests to pass, no unexpected assertion failures, correct end-to-end data comparison, and achievement of the defined coverage goals. This provides confidence that the Ethernet IP is functionally correct, robust against error conditions, and ready for further integration.
